TL;DR

We ask a coding agent to write a separate diagnostic program after each task execution in simulation. Through new viewpoints (View) and targeted physical tests (Probe), the program gathers evidence missing from execution feedback to guide task-program refinement.

How Fly-by-Code Works

Coding agents usually revise the task program from execution feedback alone, which can miss outcomes and failure causes.

View · visual evidence

Look again from a new viewpoint

When the evidence gathered during task execution leaves part of the outcome unseen, the agent writes a diagnostic program that flies the robot to new viewpoints and returns the images with its notes. What it sees helps the agent decide whether the task is done and how to revise the program. Here, after an incomplete first attempt, the program inspects the cabinet from new viewpoints to find what is missing.

Probe · physical evidence

Test the interaction

The diagnostic program runs physical tests in simulation to learn how an interaction behaves, such as how an object responds to contact, how a door opens, or how much the robot can lift. The measurements help the agent revise the program. Here, a straight pull does not open the cabinet door; pulling along a small arc about the hinge does.

Active Feedback · diagnostic program

A diagnostic program after every execution

After each execution, the coding agent writes a separate diagnostic program with the same robot APIs as the task program, using View, Probe, or both as needed. With the returned evidence and the execution logs, the agent decides to finish, or refines the code and runs the full task again from the initial state.

From simulation to the physical robot

Task programs refined in simulation transfer zero-shot to our aerial manipulator through shared robot APIs, without task-program source-code modification. Rather than replaying simulated trajectories, the deployed programs use real-world observations through the shared robot APIs to guide execution, despite differences between the simulated and physical scenes and variations in the initial robot pose.

Align: testing alternative contact points

After repeated pushes kept rotating a carton, the agent used AF to test alternative contact locations and sideways slides.

1

Agent’s recorded AF analysis: which push reduces rotation?

“My working guess is sideways friction drag.” […]

“I need controlled experiments to learn how much each action twists the carton: centre push, high-edge push, low-edge push, and a push followed by a small sideways slide while still in contact.”

2

Generated diagnostic code: compare contact actions

The program tested these actions sequentially, returning to the same viewpoint after each probe to measure the response from RGB-D observations. In the code and console below, “hi-edge” and “lo-edge” are the carton’s left and right edges in the head-on camera view, and “drag +y” / “drag -y” are small slides to the left / right.

3

Returned diagnostic views, measurements, and the agent’s image notes

The first left-edge push produced less rotation per unit of advance than the centre and right-edge pushes. Neither sideways slide reversed the rotation.
